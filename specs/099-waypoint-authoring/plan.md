# Implementation Plan: Waypoint Authoring UX

**Branch**: `099-waypoint-authoring` | **Date**: 2026-10-17 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/099-waypoint-authoring/spec.md`

## Summary

Add a player anchor for waypoint creation and replace the accumulating waypoint
button row with one creation menu. Move chain editing to the selected waypoint in the
Inspector: a filtered `Next` picker (including `(end)`) and an `Add Next` anchor menu.
A newly created waypoint gets an anchor-informed automatic name (`Player 1`,
`Camera 2`, `Origin 1`). Extending a waypoint that already has a next inserts the new
waypoint before it, preserving the chain tail. All effects reuse the existing
`WaypointCreate` and `LinkSpawn` commands, so each is one step on the existing undo
history.

## Technical Context

**Language/Version**: F# on .NET 10 (`net10.0`)

**Primary Dependencies**: Prime (symbolic data), SDL3-CS, custom cimgui binding with
native `libcimgui.so`, JoltPhysicsSharp. Existing editor modules `Spawning`,
`Selection`, `CueTree`, `Outliner`, `Inspector`; existing world modules `Zone`,
`Entity`, `Systems`.

**Storage**: In-memory zone state (`SlotMap<Waypoint>`) and the existing project
manifest; this feature adds no persisted field or format.

**Testing**: xUnit over the headless editor/world paths (`dotnet test
test/Sugoi.Tests.fsproj`). No ImGui headless harness exists; menu behaviour is
validated manually via `quickstart.md`.

**Target Platform**: Linux desktop (SDL3 window, GPU rendering, editor UI).

**Project Type**: Single desktop application with an in-engine editor.

**Performance Goals**: Keep the existing 60 FPS gameplay target; the new code runs
only while the editor is open and touches tens of waypoints per zone.

**Constraints**: All authoring is edit-mode only; play mode remains non-authoring.
No new command family and no new persisted field or format, no change to chain
resolution or viewport drawing. Every creation/link/insertion remains exactly one
undo step.

**Scale/Scope**: A zone holds tens of waypoints (existing fixed slot-map capacity).
The anchor palette is closed at Origin, Camera, Player for this feature.

## Phase 0: Research

Completed in [research.md](research.md). Key decisions:

1. Chain controls live in the Inspector (the single editing surface).
2. `LinkSpawn` is reused; insertion is implemented in `spawnLinkedWaypoint`, whose
   payload already carries both the predecessor's previous next and the new
   waypoint's captured (now linked) value.
3. One `WaypointAnchor` palette in `Spawning` serves both menus.
4. Automatic names are `<Prefix> <lowest free positive n>`, parsed by numeric suffix.
5. The player anchor reads the actor's authored transform and requires
   `Systems.isPlayerLive`.
6. Action menus are real ImGui popups; the next-chooser stays a filtered combo.
7. The next-chooser carries `(EntityRef option, name)` pairs so duplicate labels
   cannot retarget the wrong waypoint.
8. Headless tests cover data/undo behaviour; UI is validated by the quickstart.

## Phase 1: Design

Completed in [data-model.md](data-model.md) and [quickstart.md](quickstart.md).

**Model rules**

- No new persisted field or format. `Waypoint.Base.Name` carries the automatic name
  and is captured with the waypoint like any other authored name.
- Anchors: `Origin`, `Camera`, `Player`; `Player` requires a live designation.
- New waypoints use unit scale and copy the anchor's position and facing.
- Names: `<Prefix> <n>` with the lowest free positive number for that prefix among
  live waypoints; renames and deletes free a number.
- Insertion: with `A.Next = Some B`, extending `A` with `N` yields
  `A.Next = Some N` and `N.Next = Some B`; with no next, `N.Next = None`.
- Commands: `WaypointCreate` for creation, `LinkSpawn` for link-and-create (the
  captured new waypoint includes its `Next`), `Link` for next changes and unlink.
  Undo/redo needs no new runner.
- Capacity: reuse `hasRoom`; refuse before mutating and record nothing.

**UI rules**

- Outliner: one `Add Waypoint` button opens a popup of the anchor palette; the
  waypoint rows lose their per-row `Link` button and the toolbar loses its four
  actions.
- Inspector (waypoint selected): a `Next` filtered combo over `(end)` plus the zone's
  other live waypoints, and an `Add Next` popup over the same anchor palette. `At
  Player` is disabled when there is no live player; both controls are disabled at
  capacity.
- Names are computed in `Spawning` before the entity is handed to `spawnWaypoint` or
  `spawnLinkedWaypoint`, so naming and placement cannot diverge.
- The `Next` combo reports its pick through a local mutable and commits after the
  combo returns; `state` is a `byref` and cannot be captured by the picker's closure.

## Implementation Outline

1. **Bindings** (`render/ImGui.fs`): add `openPopup`, `beginPopup`, `endPopup`.
2. **Spawning**: add `WaypointAnchor`, the ordered palette, anchor labels and
   availability, the automatic-name helper, anchor entity constructors, and
   `spawnWaypointAt` / `spawnNextWaypointAt`; change `spawnLinkedWaypoint` to insert.
3. **Outliner**: replace the four-button row with one creation popup; simplify
   `slotRows` by removing the waypoint link control.
4. **Inspector**: add the waypoint chain section (`Next` combo and `Add Next` menu).
5. **State comment**: note that `ComboFilter` is shared with the next picker.
6. **Tests**: update the middle-extension test to assert insertion; add player-anchor,
   naming, capacity, selection, and undo/redo tests.
7. **Docs**: record the authoring interaction in `docs/EDITOR_DESIGN.md`.
